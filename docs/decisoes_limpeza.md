# Decisões de Limpeza e Pré-Processamento (Etapa 2)

Registro das decisões tomadas na limpeza (raw → trusted → refined), com a
justificativa de cada uma. Toda decisão nesta página existe para servir à
métrica central do projeto — cobertura vacinal por município (ver
`docs/entendimento_problema.md`) — e à confiabilidade de comparar
municípios entre si: um erro de limpeza não detectado se propaga direto
para a priorização de onde fazer campanhas de vacinação.

## Abordagens de pré-processamento utilizadas

| Abordagem | Aplicada? | Onde / justificativa |
|---|---|---|
| **Limpeza** (remoção de linhas inválidas/duplicadas, tratamento de ausentes, padronização de tipos e códigos) | Sim, extensivamente | Todas as seções abaixo (1-4): descarte de municípios sem população, validação de código de município, datas inválidas, duplicatas exatas, etc. |
| **Transformação** (derivação de novas colunas/valores a partir dos originais) | Sim | Resolução dinâmica de nomes de coluna do PNI (seção 2), conversão de código DATASUS (6 dígitos) para o padrão IBGE (7 dígitos) no cruzamento (seção 2 e 4), agregação de nível-paciente (uma linha por dose) para nível-município×mês (seção 2), cálculo de `cobertura_doses_por_100_habitantes` e `pib_per_capita_reais` (seção 3 e 4). |
| **Amostragem** (reduzir o volume processando só uma parte dos dados) | **Não** | O objetivo do projeto é cobertura *nacional completa* (todos os municípios, ano inteiro de 2025) — amostrar um subconjunto de municípios ou meses reduziria exatamente a abrangência que o projeto busca (ver `docs/criterios_selecao_dados.md`, escopo geográfico/temporal). O processamento em blocos/streaming (seção 2) é uma técnica de *implementação* para caber na memória disponível, não uma amostragem: 100% dos registros de cada arquivo são lidos e agregados, só não ficam todos em RAM ao mesmo tempo. |
| **Desbalanceamento de classes** | **Não se aplica nesta etapa** | É uma técnica de preparação de dados para classificação supervisionada (ex.: se a classe "baixa cobertura" for rara no conjunto de treino de um classificador). Esta é a Etapa 2, descritiva/analítica — ainda não há um modelo supervisionado sendo treinado. Será reavaliada na Etapa 3 (classificação, ver `README.md`) se o desbalanceamento da variável-alvo se mostrar um problema real ali. |

## 1. Dados de população (IBGE)

| Decisão | Justificativa |
|---|---|
| Remover a linha de metadados/rótulos que a API SIDRA inclui como primeira linha do CSV bruto | A API retorna por padrão (`/h/y`) uma linha com descrições dos campos (ex.: `V = "Valor"`) antes dos dados reais; sem removê-la, ela seria lida como um "município" com população não numérica, quebrando o cálculo de cobertura. Identificada comparando o raw com a documentação da API SIDRA. |
| Descartar (não imputar) municípios com população ausente/sigilosa (marcadores como `-`) | População é o denominador da métrica de cobertura vacinal. Uma imputação (média, mediana etc.) inventaria um denominador que não existe e distorceria diretamente o resultado; preferimos excluir o município da análise a apresentar um número fabricado. |
| Descartar códigos de município que não têm exatamente 7 dígitos numéricos | Padrão IBGE é sempre 7 dígitos; qualquer coisa fora disso indica erro de fonte e impediria o `join` com os dados do PNI. |
| Remover duplicatas por código de município (mantendo a primeira ocorrência) | A API não deveria retornar o mesmo município duas vezes para o mesmo ano; quando ocorre, é tratado como erro de coleta, não como dois registros válidos. |

## 2. Dados de doses aplicadas (PNI)

| Decisão | Justificativa |
|---|---|
| Processar cada arquivo mensal em streaming (blocos/chunks), nunca carregando o ZIP nem o CSV inteiros em memória | Os arquivos do PNI são nacionais e grandes (abril/2025 tem ~4GB comprimido; descompactado passa de 15-20GB): isso não cabe na RAM disponível (confirmado na prática: o processo foi encerrado por falta de memória ao tentar carregar o arquivo inteiro). A solução foi ler o objeto do MinIO em blocos, descompactar o ZIP também em streaming (biblioteca `stream-unzip`, que não precisa acessar o fim do arquivo como o `zipfile` padrão) e processar o CSV em pedaços de 100 mil linhas por vez, agregando cada pedaço antes de descartá-lo. |
| `clean_pni.py` baixa cada mês **direto da fonte** para trusted, sem nunca gravar o ZIP bruto no bucket `raw`, por padrão — em vez de exigir rodar `download_pni.py` (que grava em `raw`) antes | Tentativa inicial: baixar os 12 meses nacionais completos de 2025 para o bucket `raw` (cada mês entre 1,4GB e 5GB) esgotou o disco do ambiente (32GB) bem antes do fim do ano: só deu para baixar 7 meses (jan-jun + ago), e mesmo esses ficaram ocupando ~18,5GB desnecessariamente depois de já limpos. A correção inicial foi um script à parte, fora do fluxo documentado (`reprocessar_pni_2025.py`: baixa cada mês para um arquivo temporário local, limpa direto dali, envia só o parquet para `trusted`, apaga o temporário antes do próximo mês). Ele foi **incorporado a `clean_pni.py`** como `clean_and_upload_from_source` — a função padrão do CLI (`python -m src.cleaning.clean_pni --ano <ano>`) — porque o README e este documento já descreviam esse comportamento como o oficial, mas o código publicado ainda exigia `download_pni.py` primeiro; deixar o script à parte, não referenciado por nenhum guia, era a própria causa raiz do problema de disco para quem seguisse a documentação ao pé da letra. `download_pni.py` (grava em `raw`) e `clean_pni.py --from-raw` (lê de `raw`) continuam disponíveis para quem quiser arquivar os ZIPs brutos de propósito (ex.: auditoria). Isso permitiu processar o **ano completo de 2025 (12 meses)**, não só os 7 que cabiam com a abordagem anterior. Essa é a mesma restrição de escopo que o commit original da Etapa 1 já pretendia resolver filtrando por região (Sudeste); preferimos resolver o problema de disco em vez de reduzir a abrangência geográfica, então o dataset final é nacional e com o ano completo. |
| Resolver nomes de coluna dinamicamente (por lista de candidatos), em vez de fixar nomes | Não tínhamos os dados reais em mãos para confirmar o schema exato ao escrever o pipeline (ver `inspect_pni.py` da Etapa 1, criado exatamente por essa incerteza). Fixar nomes errados quebraria o pipeline silenciosamente ou praticamente às cegas; o resolver falha de forma explícita e lista as colunas disponíveis quando não encontra um candidato. **Confirmado contra os dados reais** (rodando `clean_pni.py` no Codespace): o schema real usa `dt_vacina` (data), `sg_imunobiologico` (nome/sigla da vacina), `co_dose_vacina`/`ds_tipo_dose` (dose) e `co_municipio_paciente`/`co_municipio_estabelecimento` (município): nenhum dos nomes hipotéticos originais batia exatamente; `COLUMN_CANDIDATES` foi atualizado com os nomes reais como primeira opção, mantendo os antigos como fallback. |
| Usar `co_municipio_paciente` (residência do paciente), não `co_municipio_estabelecimento` (onde a dose foi aplicada), como código de município | A população do IBGE (denominador da cobertura) é contada por residência. Se o numerador (doses) usasse o município do estabelecimento, cidades-polo com grandes hospitais/UBS que atendem pacientes de fora inflariam artificialmente sua cobertura, e os municípios vizinhos que enviam pacientes para lá apareceriam com cobertura subestimada: o oposto do que os dois realmente têm. |
| Descartar linhas sem código de município válido (6 dígitos, não 7) | **Bug real encontrado ao rodar contra os dados reais**: `co_municipio_paciente` traz o código de município do DATASUS/SUS, que tem 6 dígitos (o 7º dígito do código IBGE é só um dígito verificador, que o DATASUS não usa). A primeira versão do pipeline validava/preenchia como se fosse o código IBGE de 7 dígitos, o que produzia códigos de aparência válida (ex.: `0110001`) que na verdade nunca existiam no IBGE: o cruzamento com a população saía 100% sem correspondência (todo o dataset refinado aparecia com 0 doses, mesmo já tendo processado mais de 1,1 milhão de linhas de doses). Corrigido validando 6 dígitos aqui e truncando o código IBGE (7 dígitos) para 6 na hora do cruzamento em `build_coverage.py`, sem perda de informação, já que o 7º dígito do IBGE não identifica nada além do que os 6 primeiros já identificam. |
| Descartar linhas sem data de aplicação válida | A agregação é por mês; uma linha sem data não pode ser alocada a um período. |
| Detectar o formato da data por amostra (`%Y-%m-%d` vs `%d/%m/%Y` etc.) em vez de usar heurística `dayfirst` | `dayfirst=True/False` do pandas resolve a ambiguidade só parcialmente e pode inverter dia e mês silenciosamente quando o formato real do dado é o oposto do assumido; isso foi detectado durante o desenvolvimento (teste com datas ISO `2025-01-05` sendo lidas como 1º de maio). Testar qual formato explícito casa com mais valores da amostra evita esse erro silencioso. |
| Remover duplicatas exatas (linha inteira repetida), mas só dentro do mesmo bloco de streaming (chunk de 100 mil linhas) | Indicam erro de extração/join na fonte (mesmo registro exportado duas vezes), não doses reais adicionais; mantê-las infla artificialmente a contagem de doses. Limitação aceita: como o arquivo é processado em streaming (ver decisão acima), uma duplicata cujas duas ocorrências caiam em blocos diferentes não é detectada. Trade-off necessário para processar arquivos maiores que a RAM disponível; duplicatas exatas tendem a ser raras e, quando ocorrem, tendem a estar próximas no arquivo de origem. |
| Agregar para `município × mês (× vacina)` já na limpeza, em vez de manter uma linha por dose | Reduz drasticamente o volume de dados (o objetivo do projeto é município, não paciente individual) e evita manter dado de nível de paciente além do necessário. |
| Sinalizar município-mês fora de `[Q1 − 3·IQR, Q3 + 3·IQR]` como outlier, **sem remover** | Um valor muito alto pode ser um polo regional de vacinação (município que atende vizinhos), informação relevante para o objetivo do projeto (priorizar ações), não ruído a descartar. A decisão de remover ou não fica para a análise exploratória, com a coluna `outlier_iqr` disponível para essa investigação. |

## 3. PIB municipal (IBGE): variável socioeconômica

| Decisão | Justificativa |
|---|---|
| Usar PIB per capita municipal como variável socioeconômica, em vez de renda ou IDH | Renda per capita: os dados mais recentes que o IBGE divulga por essa métrica (PNAD Contínua) só descem a nível de Brasil/UF, não de município, então não dá para cruzar com a cobertura por município. IDH municipal (IDHM): só existe calculado para 2010 (Atlas do Desenvolvimento Humano/PNUD, plataforma diferente do IBGE/SIDRA, sem atualização com o Censo 2022); cruzar cobertura de 2025 com um indicador de 15 anos atrás foi considerado defasado demais. PIB per capita municipal (Tabela 5938 do SIDRA) é oficial, municipal, e tem série anual até 2023: o mais atual dos três disponível hoje. |
| Escolher a Tabela 5938 do SIDRA, não a 6784 | A 6784 parecia ser "PIB dos Municípios" pelo nome, mas a API rejeita consulta por município nela (`Parâmetro N6 (Nível territorial) incompatível com a tabela`): ela só existe a nível Brasil. Confirmado consultando `/metadados` das duas tabelas antes de escrever qualquer código de ingestão, mesmo princípio de "inspecionar antes de assumir" já usado no PNI (`inspect_pni.py`). |
| Calcular PIB per capita manualmente (`pib_mil_reais * 1000 / populacao`), em vez de usar uma variável "per capita" pronta | A Tabela 5938 só tem PIB total (variável 37, em Mil Reais) a nível de município; as variáveis "per capita" prontas do SIDRA existem só a outros níveis territoriais. Como já temos a população (IBGE, mesma fonte) coletada, calcular o per capita nós mesmos evita depender de mais uma tabela e mantém o numerador/denominador com a mesma origem de dado. |
| Cruzar PIB e população/cobertura direto pelo código de 7 dígitos, sem a conversão de 6/7 dígitos que o PNI exige | O PIB vem do próprio IBGE (Tabela 5938), mesmo sistema de código da população; não é o código DATASUS de 6 dígitos do PNI. Aplicar a conversão aqui seria um erro (e um bug bem parecido com o que já corrigimos na seção 2, mas ao contrário: truncar um código que já está certo). |
| Usar o ano de PIB mais recente disponível (2023) para cruzar com a cobertura de 2025, em vez de exigir o mesmo ano | Dado de PIB municipal sempre sai com atraso (a série do IBGE vai só até 2023, não existe "PIB de 2025" publicado); exigir o mesmo ano deixaria essa variável sempre vazia. `build_coverage.py` recebe o ano do PIB como parâmetro separado (`--ano-pib`, default 2023) do ano da cobertura (`--ano`). Essa defasagem de ~2 anos entre as duas fontes deve ficar explícita em qualquer gráfico/relatório que use `pib_per_capita_reais`. |
| Município sem PIB no trusted fica com `NaN`, não `0`, no dataset refinado | Diferente da decisão equivalente para `doses_aplicadas` (onde `0` é um sinal real: "nenhuma dose registrada"), a ausência de PIB é lacuna de dado (ex.: município sem registro naquele ano da série), não uma economia zerada; preencher com `0` fabricaria um valor incorreto para qualquer análise de correlação feita com essa coluna. |
| `build_coverage.py` prossegue sem a coluna de PIB (em vez de falhar) quando o trusted de PIB ainda não foi processado | PIB é uma variável adicional, não uma dependência obrigatória da métrica central do projeto (cobertura vacinal). Uma equipe rodando só `clean_ibge.py` + `clean_pni.py` (sem `clean_pib.py`) ainda consegue gerar o dataset refinado principal; a coluna de PIB só aparece quando `clean_pib.py` já rodou para o `--ano-pib` pedido. |

## 4. Métrica de cobertura vacinal (refined)

| Decisão | Justificativa |
|---|---|
| Métrica é "doses aplicadas por 100 habitantes", não "% de pessoas vacinadas" | O dataset agregado não separa por dose (1ª, 2ª, reforço) de forma confiável em todos os casos, então uma pessoa com 2 doses conta 2x no numerador. Chamar isso de "cobertura populacional" seria impreciso; documentamos a métrica como um proxy de intensidade de vacinação. Reavaliar na Etapa 3 se for possível filtrar por "1ª dose"/dose única. |
| Manter municípios com população no IBGE mas 0 doses no PNI (em vez de excluir) | "Sem dado de vacinação" é, em si, um sinal relevante para o objetivo do projeto (identificar áreas de baixa cobertura para priorizar ações): excluir esses municípios esconderia exatamente o que o projeto quer encontrar. Com o ano completo de 2025 processado, isso passou a ser só uma salvaguarda teórica: nenhum dos 5.571 municípios ficou com 0 doses no resultado final. |
| Cruzar população (IBGE, 7 dígitos) e doses (DATASUS, 6 dígitos) truncando o código IBGE para 6 dígitos, em vez de comparar direto | Os dois sistemas de código não são o mesmo (ver decisão equivalente na seção 2). O código de município final na camada refined continua sendo o de 7 dígitos do IBGE (mantido por ser o identificador padrão e mais reconhecível); os 6 dígitos são usados só como chave de cruzamento, descartada depois do merge. |

## 5. Integração contínua (CI)

| Decisão | Justificativa |
|---|---|
| GitHub Actions roda `pytest` a cada `push`/`pull request` na `main` (`.github/workflows/tests.yml`), sem subir MinIO no runner | Só é possível porque a limpeza foi desenhada desde o início como funções puras, sem I/O: `clean_pib_dataframe`, `_clean_and_aggregate_chunk`, `compute_coverage`, `meses_faltantes` recebem DataFrames/valores e devolvem DataFrames/valores, e só as funções finas em volta delas (`clean_and_upload`, `build_coverage`) tocam o MinIO. O CI testa exatamente a lógica de negócio, sem precisar simular a infraestrutura. |
| CI cobre só a lógica de limpeza/cruzamento, não os notebooks nem a ingestão (`download_*.py`) | Os notebooks dependem de dado real no MinIO para ter valor (o objetivo deles é explorar, não validar regra de negócio) e os scripts de ingestão dependem de rede externa (SIDRA, OpenDataSUS): automatizá-los no CI exigiria mockar serviços externos, o que foge do escopo de uma disciplina de engenharia de dados aplicada e adicionaria manutenção sem ganho proporcional de confiança. |

## 8. Coluna `ano` da população (IBGE): bug corrigido

| Decisão | Justificativa |
|---|---|
| `clean_ibge.py` preenche a coluna `ano` a partir do parâmetro `--ano` da própria limpeza, em vez de renomear uma coluna da resposta da SIDRA | **Bug real encontrado** (ao investigar uma dúvida da equipe sobre o significado do valor `9324` aparecendo na coluna `ano`): a Tabela 6579 devolve três dimensões por linha — D1 (Município), D2 (Variável, sempre `9324`/"População residente estimada", porque a URL de `download_ibge.py` já fixa essa variável) e D3 (Ano de referência) — a mesma estrutura da Tabela 5938/PIB (`clean_pib.py` já tratava D2 como variável e D3 como ano corretamente). A versão anterior de `clean_ibge.py` renomeava **D2C** (a variável) direto para `"ano"`, em vez de D3C (o ano de fato); confirmado contra o CSV bruto real, onde D3C/D3N já trazem o ano correto. Resultado: **todo o dataset de população — e, por herança do `merge` em `build_coverage.py`, o dataset refinado inteiro — ficava com `ano = "9324"` em vez do ano real (ex.: `"2024"`)**. Os testes não pegaram o problema porque a própria fixture sintética (`_linha_municipio`) já assumia esse mapeamento errado (usava `ano` como valor de `D2C`), reproduzindo a suposição equivocada em vez do formato real da API. A correção usa o parâmetro `--ano` (não D3C) para preencher a coluna, o mesmo critério já usado para particionar os dados no MinIO (`ano={ano}/...`) — os dois sempre coincidem na prática, mas evita depender de mais uma suposição sobre a posição das dimensões da API. Como a coluna não é usada para nenhum `join` (o particionamento por ano já vem do caminho no MinIO, não da coluna), o bug não afetava a métrica de cobertura em si — mas deixava um valor visivelmente errado em qualquer inspeção do dataset (`df.head()`, dicionário de dados), o tipo de inconsistência que motivaria uma pergunta direta dos orientadores. |
| Fixture de teste corrigida para refletir o formato real da API (`D2C`/`D2N` sempre `9324`/"População residente estimada", constante por linha) | A fixture antiga (com `D2C` variando por chamada, imitando um "ano") não representava a resposta real da SIDRA e mascarava o bug acima. Adicionado também um teste de regressão (`test_coluna_ano_usa_o_ano_pedido_nao_o_codigo_da_variavel_sidra`) que falha caso a coluna `ano` volte a ser lida do corpo da resposta em vez do parâmetro da função. |
| Reprocessar a população especificamente na partição `ano=2025` do `trusted`, não `ano=2024` | **Segunda camada do mesmo bug, encontrada ao validar a correção acima nos dados reais**: `build_coverage.py` usa o mesmo parâmetro `--ano` para localizar tanto a população quanto as doses (`ibge/populacao/ano={ano}/...` e `pni/ano={ano}/...`). O primeiro reprocessamento rodou `clean_ibge.py --ano 2024` (o comando padrão documentado no README para a população), o que corrigiu só a partição `ano=2024` — mas `build_coverage.py` roda com `--ano 2025` e portanto lê `ibge/populacao/ano=2025/...`, uma partição diferente que já existia no MinIO desde antes da correção (gravada com o bug) e não foi tocada pelo primeiro reprocessamento. O dataset refinado só passou a refletir a coluna `ano` correta depois de rodar `clean_ibge.py --ano 2025` especificamente. A lição: corrigir o código não é o mesmo que corrigir o dado já materializado no MinIO na partição que de fato é consumida — vale sempre conferir qual partição cada consumidor (`build_coverage.py`, no caso) realmente lê antes de considerar um reprocessamento completo. |

## 9. Achados de uma auditoria de código pós-Etapa 3

Revisão do código de `src/` feita depois da Etapa 3 estar completa (não
motivada por um erro em produção, mas por uma auditoria deliberada de
qualidade). Achados reais, cada um já corrigido e coberto por teste:

| Decisão | Justificativa |
|---|---|
| `_resolve_columns` (`clean_pni.py`) trata `vacina_nome` como opcional (como `dose` e `paciente_idade`), não mais obrigatória | **Bug real latente**: o resto do código (`_clean_and_aggregate_chunk`, `_combine_partial_aggregates`) já fazia `resolved.get("vacina_nome")` — ou seja, já estava pronto para agregar sem essa dimensão quando ausente — mas `_resolve_columns` levantava `KeyError` se a coluna não existisse, derrubando o mês inteiro como `[FALHOU]` mesmo que o pipeline pudesse continuar sem ela. Não se manifestou com os dados de 2025 (a coluna `sg_imunobiologico` sempre existiu), mas quebraria silenciosamente contra um schema futuro sem essa coluna. Teste de regressão: `test_resolve_columns_nao_falha_quando_vacina_nome_esta_ausente`. |
| Nova função `doses_sem_municipio_correspondente()` em `build_coverage.py`, chamada e logada em `build_coverage()` | `compute_coverage()` faz um LEFT JOIN a partir da população; qualquer linha de doses cujo código de 6 dígitos (DATASUS) não tem correspondência na população é descartada **silenciosamente** pelo `merge` — diferente do caso "município sem dose" (`sem_dados_pni`), que já era contado explicitamente. Um código inválido/typo no PNI ou um município fora do cadastro do IBGE para o ano perderia doses do total sem nenhum aviso. Agora `build_coverage()` imprime um `[AVISO]` com a contagem de municípios sem correspondência e quantas doses isso representa. Testes: `test_doses_sem_municipio_correspondente_detecta_codigo_sem_match` e `..._zero_quando_tudo_bate`. |
| Default de `--ano` alinhado para `2025` em `download_ibge.py` e `clean_ibge.py` (antes: `2024`) | A seção 8 acima já documenta o bug real causado por rodar população e `build_coverage.py` com anos diferentes. ## 10. Área territorial e densidade demográfica (IBGE): feature nova

| Decisão | Justificativa |
|---|---|
| Usar a Tabela 4714 do SIDRA (variável 6318, "Área da unidade territorial"), não a Tabela 1301 | As duas tabelas trazem área territorial por município, mas com anos de referência diferentes: a 1301 tem como base o Censo 2010, e a 4714 traz o dado já atualizado pelo Censo 2022 (confirmado consultando a API real das duas tabelas para São Paulo antes de escrever qualquer código — mesmo princípio de "inspecionar antes de assumir" já usado no PNI e no PIB). Cruzar uma cobertura vacinal de 2025 com uma área medida em 2010 introduziria uma defasagem maior do que necessário, já que existe uma fonte oficial mais recente do mesmo IBGE. |
| Área territorial não é particionada por `--ano` (`download_area.py`/`clean_area.py` não recebem esse parâmetro) | Diferente de população, PIB e doses — que mudam ano a ano e por isso são reprocessados/particionados por ano no MinIO —, a área de um município é, na prática, estática: não faz sentido baixar "a área de 2025" como se fosse uma série temporal. O ano que aparece nos dados (D3C da SIDRA, ex.: "2022") é o ano de referência da própria medição do IBGE, gravado como `ano_referencia_area` para deixar explícito que não é o mesmo `ano` usado no resto do dataset refinado — evita a confusão de alguém interpretar essa coluna como se fosse comparável à partição `ano=2025` do restante do pipeline. |
| Densidade demográfica (`densidade_hab_km2`) é recalculada em `build_coverage.py` a partir da população já coletada pelo próprio projeto (`populacao / area_km2`), em vez de usar a densidade que a própria Tabela 4714 devolve | A densidade pronta do SIDRA seria calculada com a população do Censo 2022 (mesma base da área), um ano diferente da população efetivamente usada no restante do dataset refinado (estimativa mais recente, ano da cobertura). Misturar duas bases populacionais diferentes dentro do mesmo dataset — uma para a métrica de cobertura, outra "escondida" dentro da densidade pronta — geraria uma inconsistência sutil e difícil de perceber numa auditoria futura. Recalcular a partir da população que o projeto já usa garante que numerador (população) e o resto das colunas do dataset refinado tenham sempre a mesma origem/ano. |
| Município sem área no trusted fica com `area_km2`/`densidade_hab_km2` em `NaN`, não `0` | Mesma decisão já tomada para PIB (seção 3): ausência de área é lacuna de dado, não um município sem território; preencher com `0` produziria uma densidade infinita/artificial e distorceria qualquer análise que use essa coluna. |
| `clean_area.py` descarta (não imputa) linhas com área ausente/inválida (`V` igual a `"-"` ou não numérico, sigilo estatístico do IBGE) | Mesmo critério de `clean_ibge.py`/`clean_pib.py`: um valor fabricado de área distorceria diretamente a densidade calculada depois em `build_coverage.py`, então é mais seguro descartar a linha e deixar a lacuna explícita (`NaN` no refinado) do que estimar um valor. |
| `build_coverage.py` prossegue sem as colunas de área/densidade (em vez de falhar) quando o trusted de área ainda não foi processado | Mesmo padrão já usado para PIB: área/densidade é uma variável adicional, não uma dependência obrigatória da métrica central do projeto. Uma equipe que ainda não rodou `download_area.py`/`clean_area.py` continua conseguindo gerar o dataset refinado principal; as duas colunas novas só aparecem quando a camada trusted de área já existe. |

## 12. Faixa de fronteira oficial (IBGE): feature nova

| Decisão | Justificativa |
|---|---|
| Usar a planilha "Municípios da Faixa de Fronteira e Cidades-Gêmeas", edição 2024, do GeoFTP do IBGE (`organizacao_do_territorio/estrutura_territorial/municipios_da_faixa_de_fronteira/2024/`), em vez de continuar aproximando por UF | Até a Etapa 3, o sinal de fronteira era 11 estados inteiros marcados como "1" (ver seção histórica em `docs/decisoes_modelagem.md`) — grosseiro por construção, já que um estado inteiro "contamina" municípios que na prática estão longe da fronteira. O IBGE publica a lista oficial por município; usá-la dá um sinal geográfico muito mais preciso sem custo adicional de coleta relevante. |
| `fronteira = 1` é `FAIXA_SEDE == "sim"` (sede do município dentro da faixa), não "município intersecta a faixa por área de alguma forma" | A planilha bruta traz uma linha por município que **intersecta** a faixa por área (590 no total, confirmado contra o arquivo real) — um universo mais amplo que o critério tradicional de "município de fronteira", que se baseia em a sede (a cidade em si) estar dentro dos 150km da linha divisória (Lei 6.634/1979). Usar `TOCA_LIM` ou `PORC_INT > 0` em vez de `FAIXA_SEDE` contaria municípios cujo território apenas encosta na faixa sem a cidade estar de fato ali — mais próximo da aproximação grosseira por UF do que de um sinal preciso. Depois de descartar as 2 linhas com `FAIXA_SEDE` indefinida sobram **588 linhas** na camada trusted — e é importante não confundir esse número com o resultado do critério: essas 588 continuam sendo *municípios que intersectam a faixa*, dos quais **511 têm `FAIXA_SEDE = "sim"`** (511 + 77 = 588). É 511, portanto, o número de municípios com sede na faixa, e é ele que vira `fronteira = 1` (502 sobrevivem aos descartes e chegam à base de modelagem, 9,3% dela). Vale registrar que 588 coincide com o número tradicionalmente citado para a faixa de fronteira brasileira, mas isso **não valida o critério**: 590 − 2 = 588 é consequência aritmética do descarte das linhas indefinidas e sairia igual qualquer que fosse o critério escolhido (`FAIXA_SEDE`, `TOCA_LIM` ou `PORC_INT > 0`), logo não consegue distinguir entre eles. O relatório de limpeza (`_cleaning_report.txt`) imprime as duas contagens separadas — `linhas_finais` e `municipios_com_sede_na_faixa` — justamente para manter a diferença explícita. |
| Município sem correspondência na tabela trusted de fronteira fica com `fronteira = 0`, não `NaN` — única exceção à regra de "ausência = lacuna, não 0" usada para PIB/área/CNES (seções 3, 10 e 11) | A fonte é uma **lista positiva completa**: todo município que intersecta a faixa de fronteira por área aparece na planilha (590 linhas), então um município que não aparece nela genuinamente não toca a faixa — a ausência já é a resposta "não", não uma lacuna de coleta. Zerar aqui não fabrica informação; PIB/área/CNES são diferentes porque a ausência ali pode ser falha de cadastro para um município que deveria ter o dado. |
| `download_fronteira.py` baixa o `.xls` bruto sem nenhum parsing (mesmo padrão de `download_area.py`); `clean_fronteira.py` faz a extração/limpeza | Preserva o princípio de "raw nunca é reescrita" já usado no resto do pipeline — a camada raw é o arquivo exatamente como o IBGE publicou, erros/linhas indefinidas incluídos. |
| Faixa de fronteira não é reprocessada por `--ano` (`download_fronteira.py`/`clean_fronteira.py` não recebem esse parâmetro) | Mesmo critério já usado para área territorial e CNES (seções 10 e 11): a lista de municípios da faixa de fronteira é redefinida por lei/decreto, não recalculada a cada coleta anual do projeto — não existe uma "faixa de fronteira de 2025" como série temporal. |
| `geoftp.ibge.gov.br` bloqueado (WAF) para a rede do ambiente de nuvem usado nesta sessão — mesmo bloqueio já documentado para a Tabela 4714 de área (seção 10) | O arquivo raw efetivamente usado neste projeto foi baixado por fora deste script (navegador ligado a uma rede sem esse bloqueio) e enviado manualmente ao bucket `raw` do MinIO. `download_fronteira.py` continua sendo a forma correta/reprodutível de obter o dado quando a rede permitir — documentado aqui para quem for rodar a pipeline de um ambiente sem esse bloqueio. |
| `build_coverage.py` prossegue sem a coluna `fronteira` (em vez de falhar) quando o trusted de fronteira ainda não foi processado, e o notebook 03 cai de volta na aproximação por UF nesse caso | Mesmo padrão de degradação graciosa já usado para PIB/área/CNES: a lista oficial é uma melhoria de precisão, não uma dependência obrigatória da métrica central do projeto. |

Seguindo o critério de "descartar, não imputar" já usado em todo o projeto, tratar esgoto como feature obrigatória descartaria quase metade do dataset de modelagem — custo desproporcional ao ganho. Água, por sua vez, tem completude alta o bastante (~97% dos municípios do próprio projeto, contra ~100% de área/CNES) para seguir o mesmo critério das demais features obrigatórias, aceitando uma perda pequena. |
| `clean_snis.py` descarta (não imputa) linhas sem o indicador de água, mas **mantém** linhas com esgoto ausente | Mesma lógica da linha acima, aplicada na limpeza: o indicador que vira feature obrigatória segue o padrão de descarte já usado para PIB/área/CNES; os indicadores que ficam só de referência (esgoto) não são descartados por ausência, porque isso inutilizaria a maior parte da tabela trusted sem necessidade — ninguém depende deles como obrigatórios. |
| Cruzar por `codigo_municipio` de 7 dígitos (padrão IBGE), não por uma chave truncada de 6 dígitos | Diferente do PNI/CNES (que usam o código DATASUS de 6 dígitos), a Base dos Dados já normaliza `id_municipio` para o padrão IBGE de 7 dígitos — mesmo sistema de código de PIB/área/fronteira, cruzamento direto sem conversão. |
| Município sem correspondência na trusted de saneamento fica com `NaN` nas três colunas, não `0` | Mesma decisão já tomada para PIB/área/CNES: ausência é lacuna de dado (município sem linha para o ano de referência, ou descartado na limpeza por falta do indicador de água), não um indicador zerado — diferente do caso da fronteira (seção 12), que é uma lista positiva completa. |
| `download_snis.py` baixa o painel histórico inteiro (todos os anos) sem parsing; `clean_snis.py` filtra para o ano de referência e faz o resto da limpeza | Preserva o princípio de "raw nunca é reescrita" já usado no resto do pipeline. Diferente de área/CNES/fronteira (arquivos já pequenos e específicos), aqui o raw é deliberadamente maior que o necessário para o ano usado — o custo de manter o histórico completo no `raw` é baixo (CSV comprimido) e evita ter que rebaixar o arquivo inteiro caso o ano de referência precise mudar no futuro. |
| Saneamento não é reprocessado por `--ano` (`download_snis.py`/`clean_snis.py` não recebem esse parâmetro) | Mesmo critério já usado para área/CNES/fronteira (seções 10-12): o ano de referência (2022) é uma decisão fixa desta integração, não uma série reprocessada a cada execução do pipeline — o SNIS sequer é atualizado desde 2023 (ver primeira linha desta tabela). |
